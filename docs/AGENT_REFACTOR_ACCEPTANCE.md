## 1. 最终结论

生产规划链已经是一个由 PydanticAI 承载的单 `PlannerAgent` 架构。Agent 使用严格 `PlannerTurn` 主动决定是请求关键营业事实，还是提交/修正 `PlanBlueprint`；地点与路线事实、网络搜索执行、分钟级时间线、最小发布不变量和最终结果持久化仍由系统拥有。普通时段、餐饮、跨天顺序和舒适度不再层层阻断，而是作为整体评价目标给 Agent 一次修正空间。

本轮审查发现旧验收报告遗漏了运行恢复、结果归属、严格模型边界、分段路线事实和真实场景合理性问题。相关问题已经修复，并通过全量自动化、生产构建和三条真实 DeepSeek + 高德链路。技术绿灯与产品可用仍分开判断：三条在线场景均得到明确终态并通过场景断言；中等强度但超过舒适目标的路线会保留为质量提示，不会伪装成“没有取舍”。

## 3. 本轮发现与修正

| 原问题 | 风险 | 修正结果 |
|---|---|---|
| 生产 API 经由旧 PydanticAI facade | “新 Agent”仍被旧客户端抽象包裹 | 删除 facade，`/plan` 直接使用 `default_planner_agent()` |
| Planner prompt 缺酒店锚点与紧凑路线事实 | Agent 取舍缺少空间证据 | 提示上下文加入酒店、分区、邻近边、远距离对与事实来源 |
| `PlanningRun` 恢复读取当前 session | 修改地点后恢复旧任务会混入新输入 | 创建运行时冻结 session、POI、决策和修订意图，恢复只读原快照 |
| 已完成运行从 session 读取最新行程 | 查询旧 `run_id` 可能返回另一轮结果 | 新增 `result_snapshot`，每个运行返回自己的最终结果 |
| 同一终态仍可覆盖产物 | 重复完成或后续异常可污染审计记录 | completed/failed 一旦写入即完全不可变 |
| 编译和最终行程仍以宽松 dict 穿过边界 | 类型化只覆盖 Agent 输出，不覆盖产品结果 | 新增嵌套严格 `CompiledItinerary` / `FinalItinerary` 并在保存前校验 |
| 不同 outing 段之间被误当作无需路线事实 | `spatial_estimate` 未计入门禁却发布 verified | 统一“真实酒店休息边界”算法；普通跨段相邻点仍请求精确路线 |
| 酒店休息段丢失事实来源 | 酒店往返估算不会触发 degraded | 保存两段路线来源/降级原因，`ReleaseGate` 逐段阻断或降级 |
| `hotel_rest` 可被 Agent 当午休或普通下午过渡 | 产生数小时空档与错误时段 | Pydantic 限制其必须位于白天与 evening/night outing 之间、使用 `evening_departure` 且必须有酒店事实 |
| 长日程可以没有正式 meal slot | 行程通过但用户看不到正常用餐安排 | 长日程强制校验正式午/晚餐槽；短夜游不误报 |
| “希望路线顺路”被抽成“希望路” | 虚构地点进入候选甚至路线 | 增加指令短语过滤和回归测试 |
| “九眼桥安排在晚上”未被时间约束解析 | 明确用户偏好被排到上午 | 增加地点在前的夜间表达解析，并加入在线时段断言 |
| 独立路线修改助手、旧 prompts 和死 helper 仍在代码库 | 形成第二条模型路线和维护歧义 | 删除无调用方 prompts、旧 revise/replan/rule-repair 代码及其历史测试；修改统一回到 PlannerAgent |
| 酒店名称被当成地址直接地理编码 | 命中错误坐标后所有酒店往返事实失真 | 酒店名改用 POI 搜索、酒店类别/名称/城市评分与歧义门槛；真实场景命中全季酒店成都四川大学店 |
| 660 分钟同时承担舒适目标和发布上限 | 合法但较满的行程被直接判失败 | 保留各强度舒适目标，将发布绝对上限统一调整为 840 分钟；超目标提示、超绝对上限阻断 |
| 烘焙店按普通餐厅承担晚餐 | B&C 被排成 90 分钟晚餐并挤占景点 | 糕饼/烘焙/bakery 归为 15 分钟 quick stop，不承接正式午晚餐 |
| 餐饮 fallback 抢占已指定晚餐餐厅 | 午餐名义存在但编译后未落地 | 先保留显式餐饮归属；大型景区跨饭点确定性转为场内用餐 |
| DeepSeek structured-output/tool 协议偶发异常 | PlannerAgent 耗时数分钟后才回退 | Agent 改为 bounded JSON text + 严格 Pydantic 适配，默认关闭 thinking 与冗余事实工具；回退保持有限且可发布 |
| 日期、预约、跨天顺序没有端到端契约 | 具体预约漏检、跨天逆序仍通过 | `TimeConstraint` 支持固定时间，顺序按全行程位置评价；日期进入 PlanningContext 和逐日营业事实 |
| 营业时间依赖模型常识 | 可能安排闭馆地点并声称 verified | 新增 `NeedFacts`、`POIFactResolver`、有界网页搜索、来源分级与 `POIAvailabilityFact` |
| 偏好规则过多且修复循环过长 | 普通体验问题反复阻断或报错 | 仅保留最小事实/时间不变量；最多一次事实回合和一次整体修正，其他偏差可解释降级 |
| 恢复检查点只记录、不复用产物 | copywriting 恢复仍重跑模型和高德 | release_gate/copywriting 复用事实、蓝图、编译行程和发布决定，只重做文案与保存 |
| 预算和人数没有实际决策作用 | 前端看似可配置但结果不变 | 从新 UserProfile 和前端删除；保留并强制填写真正影响营业判断的出发日期 |

## 4. 架构边界与旧代码结论

`backend/app/agents/planner.py` 仍包含两类兼容内容：旧客户端回归所需的手写模型调用函数，以及当前确定性上下文编译/物化仍复用的 helper。项目规则明确允许 `planning_workflow.py` 与 API 作为 dict 迁移边界，因此本轮没有为了“文件看起来新”而一次性删除这些稳定 helper。生产 API 只把 `PlannerAgent` 传入工作流，运行时会进入 typed context + `FeasibilityCompiler` 分支；旧 raw-LLM 规划函数没有生产调用方。

因此当前不存在会竞争决策权的旧 Agent，也不存在第二条生产规划工作流；剩余兼容代码是受测试约束的迁移边界，而不是活跃架构。下一次若要继续物理收缩，应先把确定性 materializer 从 `planner.py` 拆到 `planning/`，再删除旧 raw-LLM 测试入口，不能直接整文件移除。

## 5. 未覆盖边界

- 当前目录没有 `.git` 元数据，无法核对历史提交、未跟踪文件或生成可审计 diff；本报告只基于当前文件和实际运行结果。
- 在线验收覆盖成都/上海三条代表性路径，不等于所有城市、配额波动和供应商故障都已在线穷举；429、网络失败、空间估算降级和门禁拒绝仍由确定性故障测试覆盖。
- SQLite 运行恢复保证同一 `run_id`、冻结输入和终态不可变，不提供多实例分布式 exactly-once。
- PydanticAI 在 Python 3.13 测试模型下的 event-loop warning 与 Node 测试的模块类型 warning 均为非阻断提示，本轮未为消除提示而改变生产运行时边界。
