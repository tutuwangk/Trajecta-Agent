# Trajecta 旅行工作台改造记录

本次交付把产品入口整理为旅行工作台，结果以每日时间轴和地图同屏呈现。后端沿用 V3
单个 `TripPlannerAgent`，收敛执行、事实与交付责任，普通体验建议允许随已核验行程交付。
主 Agent 统筹架构与整合，三个 GPT-6.1-sol / medium 子 Agent 分别负责 Runtime、页面与可视化。

## 界面与结果

参考 [Wanderlog](https://wanderlog.com/en) 的地图与每日行程联动方式。纸白背景、墨绿主色和
少量橙色标记用于突出旅行路线；结果页使用左侧时间轴与右侧全高地图，资料编辑放入调整抽屉，预约提醒可展开。
本地成都示例可直接体验，无模型请求。

时间轴按 stop ID 连接真实 stop / leg，显示到达、离开、停留与交通时间。点击地图标记可定位
对应停靠卡片，点击卡片可选中地点，按天切换路线。真实底图支持拖动、缩放和高德导航。
瓦片失败时保留地理示意图，缺坐标的地点不会获得虚构位置，连线表示访问顺序。

坐标由 Python 在时间编译后从已选高德候选补齐。浏览器只做 GCJ-02 → WGS84 展示转换，
保留原始坐标用于导航。OSM 瓦片只加载当前可见视口，带来源标注和正常缓存；实现遵循
[官方瓦片政策](https://operations.osmfoundation.org/policies/tiles/)。坐标转换许可保留在
`frontend/lib/agent-v3-map.ts`。

## 执行与交付

资料理解、事实提炼使用受限结构化调用；地点取舍、分天、排序和草案修复由同一个规划 Agent
完成。地点、坐标、路线时长、时间算术、版本与发布资格继续由确定性 Python 管理。
固定链条为 Draft → 路线事实 → 时间线 → 运营事实 → Candidate → Assessment → Release。

默认规划模型为 Flash。每轮执行最多 24 次根模型请求、80 次工具调用、6 次压缩回合、300 秒；
近上限时预留最终提交机会。预算耗尽、工具输入修正耗尽和外部服务暂不可用保存进度并暂停。
用户继续时复用业务 run_id 和检查点，开始新一轮有上限的执行。最近一次工具输入纠错反馈
随检查点保存，续跑后进入模型上下文，成功提交后清除。成功、失败与取消终态保留。

同一地点并行读取合并实际查询，消歧决定支持批量提交，写工具串行执行。额度与认证失败
分别给出明确原因，排队请求执行前再次检查服务熔断状态。前端请求有超时、取消、串行轮询
和重复操作保护；丢失提交响应后重试复用幂等键，保存链接按工作区和运行共同恢复。

每条体验问题独立维护 `review` / `blocking`。普通时段、分天、交通、节奏和已说明原因的
地点取舍为 review。模型输出 `strength=required` 无法自动获得阻断资格。固定预约必须带
`fixed_commitment=true` 和可定位的确认／不可调整原文证据；违规或遗漏为 blocking。
“步行单段不超过 20 分钟”只设置步行上限，正常驾车路线可以通过。

已核验事实且无 blocker 的行程可以保留建议形成 Release。估算路线维持 estimated，缺失或
冲突的运营事实继续给出具体日期、地点与影响，并展示可审阅的候选时间轴。
