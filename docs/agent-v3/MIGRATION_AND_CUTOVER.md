## 决策与证据边界

原切流计划要求 30 条真实 provider 分布和 7 天稳定性。实际 Flash 分布启动 16/30 后因余额
不足停止，5 个 Release 人工复核 2/5；失败揭示的餐次时段、机场时间、用户地点名和领域错误分类
已分别增加确定性修复与回归测试。

用户随后明确要求：剩余 14 个场景不再测试，完成剩余工程工作后删除 V1/V2。因此本次切流是
显式产品决策覆盖原先的外部证据门禁，不是 30-run Gate 通过。未运行的 14 条、7 天稳定性和
已发布 5 条中的 3 条人工失败都保留为证据限制，不得在后续报告中改写成通过。

## 单栈不变量

1. 地图查询只能消费 `QueryPlan`，每个原始地点最多保留 3 个候选。
2. 每个显式地点必须是已安排、待确认、不安排或排除，并带原因。
3. 指定餐厅是带身份的真实 meal stop；显式餐次时段由来源证据补强。
4. 有机场日但缺少航班时间时，在任何地点搜索前澄清。
5. 每天显示首末锚点和完整 Stop/Leg 时间线；展示名以用户资料为准。
6. 事实只从已提交方案派生；失败必须指向地点、日期、影响与建议。
7. `degraded`、`needs_adjustment`、未闭环覆盖或歧义都不能发布。
8. Candidate、Assessment 与 Release 严格绑定当前 `run_id`。

## 回滚语义

旧执行栈不再作为运行时回滚目标。若 V3 出现 P0/P1，应停止创建新 run、保留数据库和事件证据，
修复 V3 后用同一风险矩阵回归。恢复旧代码只能通过 Git 历史进行，并视为新的迁移项目，不能在
当前进程中自动降级或双写。
