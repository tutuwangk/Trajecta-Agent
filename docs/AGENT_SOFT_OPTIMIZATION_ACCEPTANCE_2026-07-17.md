# Agent 软优化与六场景验收

日期：2026-07-17
范围：意图保真、预约/时段处理、餐饮落地、多日负载、POI 类别、发布状态、前端呈现与真实供应商全链路。

## 1. 结论

本轮没有继续增加逐条硬规则，而是把质量优化集中到规划上下文、PlannerAgent 提示、候选评分和有界候选比较：明确预约受到最高偏好权重保护，但单独冲突不再把整次规划变成运行失败；普通时段、指定餐饮、用户提及地点、分天和强度偏差作为可解释的体验问题参与一次整体修正。

最终真实 DeepSeek + 高德六场景为 `technical_success_count=6/6`、`product_pass_count=6/6`。这里的产品通过表示没有空白日、固定夜间锚点丢失、绝对时长越界、事实阻断或其他场景级失败，不等于六条路线都无需调整：重庆因明确餐饮未落地标记为 `experience_status=conflict`；成都、上海、北京、厦门为 `needs_adjustment`；杭州为 `good`。六条路线的 `fact_status` 均为 `verified`。

## 2. 核心方案

### 2.1 意图账本与规划包络

- `IntentLedger` 保存带原文证据的 `visit/time/day/order/meal` 承诺，并区分 `hard_anchor/strong_preference/soft_preference`。
- `PlanningEnvelope` 保存舒适时长、840 分钟绝对上限、受保护 POI、固定锚点、分天倾向、明确餐饮与区域聚类。
- 用户原文明确提到的普通地点也进入 soft preference；漏排不会直接失败，但会进入候选评分、体验状态和最终取舍说明。
- `planning_context_snapshot` 写入运行调试记录，真实验收可核对意图账本，而不是只验证最终 JSON。

### 2.2 Agent 与工作流

- PlannerAgent 先围绕固定锚点规划，再比较换天、区域聚合、删除可选地点和餐饮承接，不对校验问题逐条打补丁。
- 业务重规划仍最多 1 次。若模型两版都存在必去遗漏、分天错位或后续空白日，工作流只加入一个容量受控的确定性分天候选参与评分，不增加模型回合。
- 候选评分提高固定预约、分天、明确餐饮、普通漏排和空白日权重，并加入多日负载差惩罚；反馈只传递影响最大的 5 项问题。
- 指定餐饮优先承接真实 meal slot；确定性餐饮修复不覆盖已有 `source=poi`。

### 2.3 事实和体验分轴

- `fact_status=verified/degraded/failed` 只表达地点、酒店、路线、营业事实和最小发布不变量。
- `experience_status=good/needs_adjustment/conflict` 表达强度、时段、预约、餐饮、移动和分天等体验取舍。
- 固定预约冲突是最高权重体验冲突，但只要事实与时间线仍可执行，路线可以发布并明确提示；已知闭馆、事实不可用、时间线错误和超过 840 分钟仍会阻断。
- 前端分别显示“事实已核验/部分事实待复核”和“体验可再优化/偏好存在取舍”，不再用单个 `verified` 掩盖产品质量。

### 2.4 POI 类别一致性

- 模型选择的高德候选还要经过确定性类别守卫；景点查询不能因为同名而确认成酒店或服务设施。
- 没有类别兼容候选时保持 ambiguous/unmatched，不用错误的高置信匹配换取表面完整。
- 六场景验收直接读取 `FactSnapshot.hotel_anchor`。杭州真实酒店锚点为“杭州西子湖四季酒店”；“京杭大运河拱宸桥”没有再被当作酒店事实。

## 3. 六场景真实结果

命令：

```bash
backend/.venv/bin/python backend/scripts/live_acceptance_six.py --summary-only
```

脚本使用临时 SQLite，不读取或改写现有业务数据。最终六场景总耗时约 294 秒。

## 5. 剩余边界

- 只有带用户证据的高权重承诺未满足才标为 `conflict`；普通蓝图分段或舒适度偏差使用 `needs_adjustment`。本轮目标是稳定产出并按真实影响透明呈现问题，不是通过隐藏告警获得全绿。
- 普通时段偏好不会强行压过区域聚合与总时长；若用户确实有不可错过的预约，应在输入中提供具体时间，系统会把它升级为 `hard_anchor` 并以最高权重优化。
- 真实供应商输出仍会波动，因此场景级数值不是永久基准；不变量、双状态语义、循环上限和产品检查口径由自动化测试守住。
- SQLite 恢复仍是单进程语义，不提供多实例分布式 exactly-once。
