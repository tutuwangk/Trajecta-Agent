- 发布状态：`verified` 3/6，`degraded` 3/6；`degraded` 的 3 次均明确提示“营业信息来自非官方网络结果，需要出发前复核”。

### 3.1 错误类型统计

本轮没有运行级失败，因此没有 `planner_agent_failed`、`amap_*`、`itinerary_publish_blocked` 等错误码。发现的是业务质量问题：

| 问题类型 | 出现情况 | 影响 |
|---|---:|---|
| `daily_time_over_intensity_limit` | 成都、上海、北京第 3 天、厦门、重庆 | 用户强度偏好没有稳定转化为每日可接受节奏 |
| `segment_time_violated` | 成都、杭州 | 蓝图时段与编译后真实到达时间不一致，且仍可发布 |
| `long_transfer` | 重庆 | 相邻景点移动过长，不适合连续安排 |
| 酒店锚点疑似误命中 | 北京、厦门、杭州 | 起终点和酒店往返事实可能建立在错误地点上 |
| 指定餐饮未落地 / fallback 替代 | 成都、上海、北京、重庆 | UGC 中的餐饮偏好没有稳定成为路线事实 |

### 3.2 同场景复跑稳定性

为修正断言误报，6 个场景完整执行了两轮，共 12 次真实链路执行。两轮技术成功率均为 6/6，但同一 UGC 的规划内容发生明显变化：

- 第一轮 6 次均为 `degraded`；第二轮变为 `verified` 3 次、`degraded` 3 次。
- 成都从 685 分钟变为 587 分钟；北京从三天均接近 800 分钟变为 640/530/728 分钟；重庆的日期分配也发生变化。
- 这说明当前外部事实和模型输出波动没有破坏终态，但会改变路线质量，尤其是每日分配和强度。

因此，“能落到终态”已经具备迁移基础；“同样输入稳定得到合理路线”尚未成立。

## 4. 产品经理视角的问题归纳

### P0：地点与酒店事实边界不可靠

北京、厦门、杭州出现与用户酒店不一致或明显无关的识别结果。酒店一旦误命中，所有酒店出发、回程和休息段都会建立在错误锚点上。当前应把酒店核验结果、候选地址和置信度直接展示给用户；低置信或类别不一致时，不应让结果以“酒店已确认”的体验交付。

### P0：高严重度时间问题仍可进入 `verified`

成都和杭州存在 `segment_time_violated`，但仍可得到 `verified`。架构上可以允许软质量问题发布，但“高严重度时段违规”和“事实已核验”不能共用一个不加解释的成功状态。建议至少拆分“事实状态”和“体验质量状态”，或在结果页明确显示“事实 verified、行程需调整”。

### P1：用户意图的日内/跨天结构没有被稳定保留

成都的上午/下午安排、重庆的分天安排、杭州的区域分组均被模型重新排列或稀释。当前系统能识别地点和必去点，但对“哪天、哪个时段、留白多少”的意图约束还不够强。需要把强时间偏好、弱时间偏好和可自由重排的地点分层保存，并在编译后做端到端回验。

### P1：餐饮是地点识别结果，不是稳定的路线决策

多次出现指定餐厅变成 `fallback_nearby`，或只留下 `meal_slots` 而没有明确餐厅项。用户输入“想吃哪家”与“只要附近吃饭”应是不同优先级；餐饮落地后还需验证营业时段、距离和正餐/quick stop 类型。

### P1：产品质量断言覆盖面不足

北京通过现有机械断言，但仍有酒店锚点和指定餐饮未保真的问题；杭州的三日路线分配明显偏空，断言也没有拦截。当前断言应补充：

- 用户明确指定的酒店与最终酒店锚点一致性；
- must / preferred / removable 地点的覆盖与未采用原因；
- UGC 中明确的日内时段与跨天安排；
- 餐厅是否真正落入时间线，而不只是生成 meal slot；
- 每日节奏平衡、跨区移动、留白日和路线目标覆盖；
- `verified` 结果中是否存在高严重度业务质量问题。

### P2：外部事实波动会转化为路线波动

两轮复跑的技术终态稳定，但路线和 `verified/degraded` 状态发生变化。对于可迁移性，必须把不变的产品不变量与可变的推荐排序分开：硬约束、酒店、必去点、时段、餐饮归属应稳定；非必去点排序才允许有波动。

## 5. 对“是否能够顺利跑通全流程”的判断

可以确认：当前生产链路能够跨城市、跨天数、跨强度和跨交通偏好完成“创建 → 识别 → 规划 → 持久化终态”的完整运行，且本轮没有运行级报错。`PlannerAgent`、事实层、编译器和 `ReleaseGate` 的有界闭环具备跨场景运行能力。

不能确认：当前系统已经具备稳定的产品级旅行规划能力。6 个场景均需要不同程度的人工复核，其中 4 个存在明显不合理安排，另外 2 个虽可执行但没有完整保留用户资料。技术迁移成功不等于场景质量迁移成功。
