# WP8 修复 R0～R4 执行记录

日期：2026-07-18

## 结论

R0～R4 已完成实现和本地验证。修复目标不是继续增加发布阻断规则，而是让运行时吸收可恢复冲突、让 Agent 在预算收敛阶段仍有决策空间，并让验收数据能够区分首次失败、重试恢复和真实成功。

真实多日酒店场景已重新运行并发布成功。原验收中“同一模型回合内两个版本化写工具共享旧 `expected_version`，最终抛出 `UnexpectedModelBehavior`”的问题未再出现。

## R0：固化失败并重定义可靠性边界

- 新增同一模型回合连续搜索、地点解析和游览画像写入的回归测试。
- 将模型协议故障与可恢复的 action/output repair exhaustion 分开：前者仍为 `failed`，后者收敛为带诊断的 `incomplete`，不再把业务可恢复失败抛到 API/脚本外。
- 同一 Workspace 只允许一个活跃写 Run，避免跨 Run 竞争制造伪并发问题。

## R1：移除模型可见版本锁

- 从模型工具 schema 中移除 `expected_version`。
- 版本仍由 Repository 以 CAS 方式拥有，但在每次工具执行时读取当前 Workspace 版本。
- 增加 `estimate_visit_profiles` 批量工具，使同一事实类别可以一次提交多个地点，并允许部分地点不可估算。
- 工具结果使用 `run_id + tool_call_id` 记录并复用，恢复时优先回放已完成结果。

这解决的是责任边界：版本一致性是 runtime concern，不应要求模型预测并维护数据库并发令牌。

## R2：把预算从异常门禁改为收敛策略

- 重复调用、预算保留和无进展不再抛 `BudgetExhausted`。
- 被限制的工具返回结构化 `tool_unavailable_in_convergence`，同时给出可继续采取的动作。
- 只有绝对墙钟上限仍是运行时硬停止。
- 工具签名、进展信号和已消耗时间持久化，恢复后不重置收敛判断。

真实复验轨迹出现 `tool_deferred_for_convergence` 后仍成功发布，说明预算控制已从“中断流程”变成“缩小行动空间”。

## R3：缩小真正的发布阻断面

- 推荐游览窗口未满足改为 experience issue。
- 超长游览日改为非阻断体验风险。
- 高召回地点提及不再默认全部必须解析；只有 Agent 实际用于路线的请求地点才需要进入发布候选。
- 地点提及增加 role、polarity 和 route relevance，使上下文地点、排除项和参考项不会自动升级为硬约束。
- Prompt 明确：普通窗口、强度和体验偏好由 Agent 权衡；已知闭馆、真实身份、时间顺序和用户明确固定预约才是硬边界。
- Release 继续发布可执行路线，同时把非阻断问题写入 `experience_issues`。

## R4：修复验收可观测性

- Live eval 支持逐 case 原子 checkpoint、进度输出和 `--resume`。
- 评分同时报告 attempted coverage、successful coverage、first-pass error rate 和 recovered cases；重跑成功不再擦除首次供应商错误。
- 新增持久化 WP8 runner：每次尝试保留领域数据库、provider transcript、事件、Workspace 和 Release 快照；单案例异常不会终止整个批次。
- 新增 V2/Legacy shadow pair 和匿名 A/B 盲测包生成器。
- 原真实链路脚本的 deterministic fallback 指标改为从事件轨迹计算，不再写死为 `False`。

## 尚未宣称完成的部分

- 本次真实复验是一条阻断故障回归，不等于 WP8 的 30 次全链分布和 65% 盲测 Gate 已通过。
- tool effect journal 已能支持恢复复用，但领域 mutation 与 effect journal 尚未合并为同一个数据库事务；极窄的“mutation 已提交、journal 尚未写入即崩溃”窗口仍需在后续 durability 工作中消除。
- Provider request/token 计数尚未作为完整账本跨恢复累积；当前已持久化墙钟、工具签名和进展状态。

因此当前结论是：R0～R4 修复已完成，原阻断问题已通过真实链路回归；WP8 总体验收仍应使用新的批量运行器重新执行，不能据单次成功提前切流。
